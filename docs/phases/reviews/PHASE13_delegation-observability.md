## 리뷰가 실제로 잡은 것 (라운드별 대표)

- **Task 2 라운드 1~2**: `emit()` 반환값이 호출부 실패 전파를 삼킴, 기록 실패 무신호,

- **Task 3 라운드 1 (3인 합의 🔴)**: 캡 기준 시각이 모델 시도마다 리셋 →
  실효 상한이 `체인 길이 × 3600초`(default 5모델 = 5시간). 지시서가 "위임 하나의 **총** 벽시계"라고
  명시했고 exit 8 의 근거까지 적었는데도 구현이 루프 안에서 리셋했다 → `reject_cause: model`.
- **Task 3 라운드 2 (silent-failure-hunter)**: 위임이 계약 밖에서 끼워 넣은 비밀번호 가드가
  전역 `$MODE` 만 봐서 **시도 단위 폴백 경로에서 여전히 유출**. 절반만 작동하는 안전장치였다.

## 계약 밖 변경의 처리 — Task 3b 를 만든 이유

Task 3 수정 위임이 지시서에 없던 `[ "$MODE" = "attach" ] || unset OPENCODE_SERVER_PASSWORD` 를
끼워 넣었다. 리뷰어 3인이 각각 확인한 결과:

- **동기는 정당**했다 — `secrets.env` 를 `set -a` 로 소싱하므로 standalone 자식이 서버 비밀번호를
  상속하는 실재 경로가 있었고, 그것이 앞서 관측된 `test_password_is_absent_in_standalone_mode`
  간헐 실패의 정체였다.
- **구현은 절반**이었고 **전용 테스트가 없었다**.

되돌리는 대신 **Task 3b 로 분리**해 오케스트레이터가 결정론적 동결 테스트를 쓰고 위임이 완결했다.
세 리뷰어 모두 무지적 통과. 교훈: 계약 밖 변경은 기계적으로 되돌릴 것이 아니라
**근거를 검증한 뒤 테스트로 승격하거나 제거**한다.

## 이 페이즈가 자기 자신에 대해 알아낸 것

- **동결 사본은 이 페이즈의 개선을 받지 못한다** — `.wrapper` 로그를 만든 페이즈인데 정작
  이 페이즈의 위임에는 `.wrapper` 가 없다 (PITFALLS 32).
- **`reject_cause` 는 첫 데이터를 스스로 만들었다** — 이번 페이즈의 반려 3건이 모두 `model`.
  같은 지시서로 상위 모델이 통과한 것이 아니라 **같은 모델이 반려 지적을 받고 고쳤다**는 점에서,
  다음 페이즈가 tier 정책을 논하려면 표본이 더 필요하다.
- **리뷰어의 계약 3항이 작동했다** — "구현자 주장을 코드로 재검증하라"가 없었다면
  Task 3 의 🔴(캡 리셋)은 "변이 검증 통과" 보고에 묻혔을 것이다. 실제로 변이 검증은
  지시서가 요구한 범위만 검증했고 캡 리셋은 그 범위 밖이었다.
